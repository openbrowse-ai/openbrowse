**Stop runaway automatic context compaction on large-context models.** A conversation that crossed the compaction threshold once could keep auto-compacting every ~30 seconds indefinitely — visibly re-summarizing and re-injecting a "Continue where you left off" turn on a chat that wasn't long enough to warrant it, most noticeably on 1M-token models.

Three independent defects compounded into the loop:

- **Repeat compactions summarized the wrong history.** `runCompaction` built its prunable view from the renderer's `messages` — the full UI transcript, which deliberately retains every pre-compaction message so the user can still scroll back. So the second pass re-selected the *original* head that the first pass had already summarized, produced a near-identical summary, and left context occupancy unchanged. Auto-compaction now runs `filterCompactedMessages` first, so each pass starts from the same compacted history the model actually sees; manual `/compact` stays a whole-history operation by design.

- **Loop protection was purely time-based.** `shouldDebounceCompaction` only suppressed a re-run within `COMPACTION_DEBOUNCE_MS` (30s), so once persisted usage sat above the threshold, the cycle resumed on the next completed turn — forever. Added a progress invariant (`hasCompactionHeadProgress`): if the newly selected head contains nothing but the previous compaction marker and its summary, summarizing it again cannot shrink context, so the attempt is skipped. Unlike the debounce this blocks unchanged re-entry permanently, while still allowing compaction once genuinely new head content accumulates.

- **The threshold could be computed from bad limits.** `getUsableTokens` returns `contextWindow - maxOutputTokens - 20_000`, and usage snapshots persist `contextWindow: 0` when the service worker can't resolve model metadata — yielding a *negative* ceiling that makes every finished turn eligible for compaction. Both non-positive limits and mutually incompatible positive ones (`maxOutputTokens` + buffer >= `contextWindow`, which real small-window models like Gemini Nano and the smallest WebLLM builds declare) now fall back to the default ceiling, so proactive compaction simply stays off for models with no headroom to summarize into; a genuine overflow is still recovered by the overflow-triggered path. The "context too small" agent-eligibility gate keeps its old meaning via a dedicated `hasCompactableContext` predicate. Relatedly, the post-turn check paired the SW-persisted `contextWindow` with `maxOutputTokens` read from the renderer's `getCurrentModelDef()`, which the agent loop no longer mutates under SW-host; `ConversationUsage` now records the output ceiling of the model the SW actually used, with the renderer value kept only as a fallback for pre-existing conversations.

`findCompactionEvents` also no longer requires a truthy `summary` flag on the summary assistant message, only that it isn't explicitly `false`. Persisted rows carry `summary: true`, but in-memory AI SDK UI messages have no such field — matching how `compacting-transport.ts` already detects compaction events structurally — so the same detection now works on both shapes. This is what lets the renderer reuse `filterCompactedMessages` against its live message list.

**Test surface.** +4 tests in `compaction.test.ts`: the compacted-view head selection and summary-only re-entry rejection (modeled on a 1M-context / 128K-output model through a full compaction + synthetic-continue cycle), the head-progress invariant releasing once new content lands, and threshold math for both real 1M limits and the unresolved-zero snapshot. All 2,690 tests pass; `tsc --noEmit` clean.
